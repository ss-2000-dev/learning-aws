# 環境別アクセス制御

開発・検証・商用の環境があり、検証環境はベースアカウント自身が兼ねる（開発・商用のみ別アカウント）構成のとき、**商用環境だけ特定ユーザーに限定してアクセスを許可する**方法。

## 重要な制約: 信頼ポリシーの Principal に IAM グループは指定できない

IAM ロールの信頼ポリシー（`AssumeRolePolicyDocument`）の `Principal` には、**IAM ユーザー・IAM ロール・AWS アカウント・フェデレーションプロバイダーは指定できるが、IAM グループは指定できない**。

そのため「`ProdOperators` グループに入っている人だけ商用ロールを引き受けられる」という制御を、信頼ポリシー側だけで直接表現することはできない。制御は次の2段構えで行う。

## 開発環境との違い一覧

商用環境の仕組みは、[05-スイッチロールの権限モデル.md](./05-スイッチロールの権限モデル.md) で説明した「① 送り出し側の許可」「② 受け入れ側の信頼ポリシー」という同じ2つの関門を使う。開発環境との違いは、**その2つとも絞っている**という点だけ。

| | 開発アカウント（Dev） | 商用アカウント（Prod） |
|---|---|---|
| ① ベースアカウント側の許可 | `Developers` / `Infra` グループ全員が持つ | `ProdOperators` という別グループの人だけが持つ |
| ② ターゲット側の信頼ポリシー | `TrustedPrincipalArns` = **ベースアカウントの root**（アカウント全体を信頼） | `TrustedPrincipalArns` = **個別ユーザーの ARN を列挙**（例: taro, hanako だけ） |

Dev は「アカウント全体を信頼して、実際の絞り込みは①のグループ分けに任せる」という緩い設計でも許容範囲だが、Prod は①と②の**両方**を絞ることで、片方が誤って緩んでも（＝設定ミス）、もう片方が食い止める作りになっている。

### 3人のユーザーで実際に追ってみる

- **taro.yamada**（`ProdOperators` に正しく所属）: ①で `sts:AssumeRole` 許可あり → ②で信頼ポリシーの ARN リストにも載っている → **両方通過、商用アクセス成功**
- **hanako.suzuki**（`ProdOperators` に入っていない）: ①の時点で `sts:AssumeRole` の許可自体を持っていない → **①でブロック**。②にすらたどり着けない
- **jiro.tanaka**（仮に、担当者が誤って `ProdOperators` に追加してしまったとする）: ①は通過してしまう（ミス） → しかし②の信頼ポリシーの ARN リストに jiro は載っていない → **②でブロック**

jiro の例が重要。**①のミス（誤ったグループ追加）が起きても、②（商用アカウント自身の信頼ポリシー）が最後の砦として機能する。** これが「商用アカウント側の安全性は、商用アカウント自身の設定だけで担保される」という設計の狙い。

## 2段構えのアクセス制御

### 1段目: ベースアカウント側（送り出す側）— グループ分けで権限を絞る

[templates/staging-account-assume-role-policies.yaml](./templates/staging-account-assume-role-policies.yaml) の設計:

- 既存の `DevelopersTestGroup` / `InfraTestGroup`（検証環境の直接権限を持つグループ）には、開発環境ロールへの `sts:AssumeRole` のみを追加で許可
- 商用環境ロールへの `sts:AssumeRole` は、別建ての `ProdOperators` グループにのみ許可
- 通常のメンバーは `ProdOperators` に入れないことで、商用ロールへの AssumeRole 権限自体を持たせない

これが最初の関門。`ProdOperators` に入っていないユーザーは、そもそも商用ロールに対して `sts:AssumeRole` を呼ぶ権限がない。

### 2段目: 商用アカウント側（受け入れる側）— 信頼ポリシーの Principal を個別ユーザーに限定する

[templates/target-account-roles.yaml](./templates/target-account-roles.yaml) の設計:

- 開発環境: `TrustedPrincipalArns` に**ベースアカウントの root**（`arn:aws:iam::111122223333:root`）を指定し、アカウント全体を信頼する。実際のアクセス制御は1段目（グループ分け）に任せる
- **商用環境: `TrustedPrincipalArns` に許可したい個別の IAM ユーザー ARN のみを列挙する**（アカウント全体を信頼しない）

```yaml
# 商用環境デプロイ時のパラメータ例
TrustedPrincipalArns: arn:aws:iam::111122223333:user/taro.yamada,arn:aws:iam::111122223333:user/hanako.suzuki
```

これが2つ目の関門。**たとえベースアカウント側で誤って `ProdOperators` に不適切なユーザーを追加してしまっても、そのユーザーの ARN が商用ロールの信頼ポリシーに載っていなければ AssumeRole は拒否される**。1段目のミスを2段目が食い止める、多層防御の構成になっている。

### なぜ2段構えにするのか

1段目（グループ分け）だけだと、ベースアカウント側の IAM 管理者がグループへの追加を誤るだけで商用環境にアクセスできてしまう。2段目（信頼ポリシーの個別ユーザー指定）を商用環境側に置くことで、**商用環境の安全性が「商用アカウント自身の設定」だけで担保される**（ベースアカウント側の運用ミスに依存しない）。

## 追加の防御: MFA 必須化

[templates/target-account-roles.yaml](./templates/target-account-roles.yaml) の `RequireMfa` パラメータを商用環境のみ `true` にすることで、信頼ポリシーに以下の `Condition` が追加される。

```yaml
Condition:
  Bool:
    aws:MultiFactorAuthPresent: "true"
```

これにより、**ベースアカウントで MFA 認証済みのセッションでなければ商用ロールへのスイッチロールができなくなる**。IAM Identity Center 移行検討時に扱った MFA 強制の考え方（[../../IAMIdentityCenter/06-MFA設定.md](../../IAMIdentityCenter/06-MFA設定.md)）と同じ発想を、スイッチロールの文脈で実現したもの。

## まとめ

| 対策 | 設定場所 | 目的 |
|---|---|---|
| グループ分け（`Developers`/`Infra` vs `ProdOperators`） | ベースアカウント | 商用ロールへの AssumeRole 権限自体を、限られたユーザーにしか付与しない |
| 信頼ポリシーの Principal を個別ユーザーに限定 | 商用アカウント | ベースアカウント側の設定ミスに関わらず、商用アカウント側だけで安全性を担保する（本命） |
| MFA 必須化（`aws:MultiFactorAuthPresent`） | 商用アカウント | 商用ロールへの切り替え自体に MFA 認証済みを要求する |

> 上記は `templates/staging-account-assume-role-policies.yaml` / `templates/target-account-roles.yaml` を分けて使う場合の説明。[templates/switch-role-all-in-one.yaml](./templates/switch-role-all-in-one.yaml)（統合テンプレート）を使う場合も `DeploymentTarget` パラメータで同じ2段構えの設計を実現しており、考え方はそのまま当てはまる（[03-移行手順.md](./03-移行手順.md) の「フェーズ 1・2 の代替」参照）。
