# スイッチロールとは

## 一言でいうと

**サインイン中の IAM ユーザー（または既に引き受けているロール）が、一時的に別の IAM ロールに“なりすまして”そのロールの権限で操作できる機能。** 多くの場合、別の AWS アカウントにあるロールに切り替えて、アカウントをまたいで操作するために使う。

マネジメントコンソール右上のアカウント名メニューから「Switch Role（ロールの切り替え）」を選ぶ操作、と言えば見たことがある人も多いはず。裏側では AWS STS（Security Token Service）の `AssumeRole` という API が呼ばれている。

## 仕組み

スイッチロールが成立するには、**2箇所の許可が両方そろっている必要がある**。

```
[ベースアカウント]                          [ターゲットアカウント（例: 商用環境）]
  IAM ユーザー                                  IAM ロール
  taro.yamada                                   ProdDevelopersRole
      │                                              │
      │ ① sts:AssumeRole を許可する           ② 「誰の AssumeRole を受け付けるか」
      │   IAM ポリシーを taro.yamada に付与      を定義する信頼ポリシー
      │   （送り出す側の許可）                   （受け入れる側の許可）
      └──────────────── AssumeRole ─────────────────►
                                                       ↓
                                          一時的な認証情報（STS トークン）が発行される
                                          taro.yamada は ProdDevelopersRole の権限で操作できる
```

1. **送り出す側（ベースアカウント）**: ユーザーに `sts:AssumeRole` アクションを許可する IAM ポリシーをアタッチする。対象はターゲットロールの ARN を指定する
2. **受け入れる側（ターゲットアカウント）**: ロールの「信頼ポリシー」（`AssumeRolePolicyDocument`）に、どの Principal（誰）からの `AssumeRole` を受け付けるかを定義する

どちらか一方だけでは成立しない。両方の許可がそろって初めてスイッチロールできる。

## 何が嬉しいのか

- **IAM ユーザーをアカウントの数だけ作らなくてよい**: ベースアカウントに1人分のユーザーを作れば、権限さえ整えればどのアカウントにも切り替えて入れる
- **一時的な認証情報**: スイッチロールで得られる認証情報は STS の一時トークンであり、有効期限が切れれば自動的に失効する（長期的なアクセスキーを配る必要がない）
- **監査性**: CloudTrail のログにスイッチロール元・先の両方の情報（`AssumedRoleUser`、`SourceIdentity` 等）が残るため、誰がどのロールで何をしたか追跡できる

## IAM Identity Center との違い（参考）

[../../IAMIdentityCenter/](../../IAMIdentityCenter/) で検討していた IAM Identity Center の Permission Set も、内部的にはこのスイッチロール（AssumeRole）と同じ仕組みの上に成り立っている。Identity Center は「信頼ポリシーの設定」「ユーザーごとのポリシーアタッチ」といった手作業を、Permission Set と Account Assignment という抽象化によって一元管理してくれるレイヤーだった。

今回はその一元管理レイヤー（Identity Center）が組織側の制約で使えないため、Identity Center が裏側でやってくれていたこと（信頼ポリシーの設定・AssumeRole 権限の付与）を、IAM ロール／ポリシーとして自分たちの手で組み立てる、というのが今回の移行の位置づけになる。
