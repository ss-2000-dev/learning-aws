# スイッチロールの権限モデル

「スイッチロールをすると、各環境にあるIAMポリシーを利用できるのか？」という疑問への回答。[templates/switch-role-all-in-one.yaml](./templates/switch-role-all-in-one.yaml) を題材に、権限がどう決まるかを詳しく解説する。

## 結論

**はい、使えます。というより、それこそがスイッチロールの本質です。** スイッチロール後は、切り替え先の環境（ロール）が持つIAMポリシーだけが有効になります。元々自分がいたアカウント側の権限は完全に無関係になります。

## 核心となる考え方: 「別人になりすます」

スイッチロールは、`taro.yamada` というIAMユーザーの権限に何かを「足す」操作ではない。**一時的に `DevelopersRole` という別の身分証明書（一時的な認証情報）に切り替える**操作。切り替えた後は、taro自身が誰であるかは一切関係なくなり、「今どのロールを装っているか」だけで権限が決まる。

## テンプレートを2つの引き出しに分けて読む

`switch-role-all-in-one.yaml` には、性質の異なる2種類のポリシーが混在している。ここを区別できるかどうかが理解の分かれ目になる。

### 引き出し①: 「実際に使える権限」— ターゲット環境側だけが持つ

`target-account-roles.yaml` 相当の部分（`Condition: IsTargetEnvironment`）。

```yaml
DevelopersRole:
  ManagedPolicyArns:
    - arn:aws:iam::aws:policy/PowerUserAccess   # ← これが「実際に使える権限」
```

```yaml
InfraRole:
  Policies:
    - PolicyName: InfraResourcePolicy
      PolicyDocument:
        Statement:
          - Effect: Allow
            Action: [ec2:*, elasticloadbalancing:*, ...]   # ← 実際に使える権限
          - Effect: Deny
            Action: [iam:*, organizations:*]                # ← 実際に使える権限（の制限）
```

**開発アカウントでEC2やS3を操作できるかどうかは、100%この `DevelopersRole` / `InfraRole` が持つポリシーだけで決まる。** taroが検証環境で `PowerUserAccess` を持っていることは、ここでは一切考慮されない。

### 引き出し②: 「切り替える許可」— ベースアカウント側が持つのはこれだけ

`staging-account-assume-role-policies.yaml` 相当の部分（`Condition: IsStaging`）。

```yaml
AssumeDevDevelopersRolePolicy:
  PolicyDocument:
    Statement:
      - Effect: Allow
        Action: sts:AssumeRole        # ← これしか許可していない
        Resource: !Ref DevDevelopersRoleArn
```

このポリシーの `Action` を見ると、`ec2:*` も `s3:*` も一切書かれておらず、**「`DevelopersRole` というロールに変身してよい」という許可だけ**を与えている。EC2を操作する権限そのものはここには一切含まれていない。

## もう1つの関門: 信頼ポリシー（受け入れ側）

`DevelopersRole` 自身の中にも、`AssumeRolePolicyDocument` という別のポリシーがある。

```yaml
AssumeRolePolicyDocument:
  Statement:
    - Effect: Allow
      Principal:
        AWS: !Ref TrustedPrincipalArns   # ← 「誰の変身なら受け入れるか」
      Action: sts:AssumeRole
```

これは「開発アカウント側が、誰からの `AssumeRole` 要求を受け入れるか」を定義している。①（ベースアカウント側の許可）と②（開発アカウント側の信頼ポリシー）の**両方**が揃って初めてスイッチロールが成立する。

## taro.yamadaを例に、実際の1リクエストを追ってみる

1. taroが開発アカウントの `DevelopersRole` へ「ロールの切り替え」を実行
2. AWSがまず①をチェック: taroの所属する `DevelopersTestGroup` に `AssumeDevDevelopersRolePolicy`（sts:AssumeRoleのみ）がアタッチされているか → ある → 通過
3. 次に②をチェック: `DevelopersRole` の信頼ポリシーが、taroが属するベースアカウントをPrincipalとして許可しているか → している → 通過
4. STSが一時的な認証情報を発行。taroは今「開発アカウントの `DevelopersRole`」という身分になる
5. taroが `ec2:RunInstances` を呼ぶ → 評価対象は**`DevelopersRole` にアタッチされた `PowerUserAccess` のみ**。taro個人や検証環境側の権限は一切関与しない

もし①のグループ所属がなければ、taroはそもそも `sts:AssumeRole` 自体を呼べず、②にたどり着く前に拒否される。逆に①を持っていても、②の信頼ポリシーに載っていなければ拒否される（[04-環境別アクセス制御.md](./04-環境別アクセス制御.md) の「2段構えの防御」の正体）。

## まとめ

| | 何を持つか | 何を許可するか |
|---|---|---|
| ベースアカウント側のグループ | `sts:AssumeRole` 権限**だけ** | 「変身してよい」という許可 |
| ターゲット環境側のロール | `PowerUserAccess` 等の**実際の権限** | 変身した後にできる操作そのもの |

「各環境のIAMポリシーを利用できるか」という質問への答えは、**「利用できる、というよりそれ以外の権限は一切使われない」**が正確な表現。
