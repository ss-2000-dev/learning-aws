# CloudFormation 管理方針

「IAM Identity Center のどこまでを CloudFormation で管理すべきか」を整理する。

## 判断基準

1. **CloudFormation リソースとして存在するか**（存在しなければそもそも選択肢にならない）
2. **変更頻度は低いか**（組織のロール構造に由来する変更）／**高いか**（入社・退社・異動に由来する変更）
3. **個人情報（PII）を含むか**（Git リポジトリに平文で置くべきでないデータかどうか）
4. **レビュー・監査の価値が高いか**（「誰が・どのアカウントで・何ができるか」を統制する情報かどうか）

この 4 つの基準で見ると、Identity Center のリソースは自然に「骨格（構成）」と「人に関するデータ（運用）」に分かれる。

## CloudFormation で管理するもの

| リソース | CFN リソースタイプ | 理由 |
|---|---|---|
| グループ定義 | `AWS::IdentityStore::Group` | 現行の IAM グループと同じく、組織のロール構造を表すもので変更頻度が低い。既に CFN で管理している資産をそのまま引き継げる |
| Permission Set（権限定義） | `AWS::SSO::PermissionSet` | 現行の「IAM グループにアタッチする IAM ポリシー」に相当。権限の中身は必ずレビューを通すべき重要情報 |
| Account Assignment（権限の割り当て） | `AWS::SSO::Assignment` | 「どのグループが・どの Permission Set を・どのアカウントに対して持つか」の一覧。マルチアカウント統制の核であり、IaC で一元管理してこそ価値が出る |
| ABAC 属性設定（利用する場合） | `AWS::SSO::InstanceAccessControlAttributeConfiguration` | 属性ベースアクセス制御のルール自体は構成情報であり、権限設計の一部 |

これらは現在すでに「グループ／ポリシーは CloudFormation」というルールで運用している対象の延長にあり、同じ考え方をそのまま踏襲できる。

## CloudFormation で管理しないほうがよいもの

| 対象 | 理由 |
|---|---|
| **ユーザー**（氏名・メールアドレス等） | **CloudFormation に `AWS::IdentityStore::User` に相当するリソースタイプが存在しない**（2026年時点）。技術的に選択肢がない。加えて、氏名・メールアドレスなどの PII を Git リポジトリで平文管理するのはセキュリティ・プライバシー上望ましくない |
| **グループメンバーシップ**（ユーザーがどのグループに所属するか） | `AWS::IdentityStore::GroupMembership` というリソース自体は存在するが、入社・退社・異動のたびに「テンプレート変更 → PR → レビュー → デプロイ」が発生することになり、人事異動のスピードに IaC のプロセスが追いつかない。運用が形骸化しやすい |
| MFA デバイス登録・パスワード等のセルフサービス操作 | ユーザー個人のセキュリティ設定であり、構成管理（インフラのあるべき姿）の対象外 |

### 例外

変更頻度が極めて低く、かつ強い監査証跡が必要なグループ（例: break-glass 用の緊急管理者グループ、セキュリティ管理者グループ）については、メンバーを絞った上であえて `GroupMembership` を CFN 管理し、変更を PR ベースでレビューさせる、という運用もあり得る。ただし対象は少数グループに限定し、一般的な部署・チームのグループには適用しない。

## 結論

- **骨格（構成・権限設計）＝ CloudFormation**: グループ定義 / Permission Set / Account Assignment
- **人に関するデータ（運用）＝ コンソール or スクリプト**: ユーザー作成 / グループメンバーシップ

Excel 台帳が担っていた「誰がいるか」の管理は、CloudFormation テンプレートではなく **Identity Center のユーザー一覧（コンソール／API）を正とする運用** に置き換える。台帳を CFN 化するのではなく、台帳そのものを廃止する、という発想の転換がポイント。
