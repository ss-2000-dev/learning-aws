# 現状整理と全体方針

## 現状の管理体制

| 対象 | 管理方法 |
|---|---|
| IAM ユーザー（誰がいるか） | Excel 台帳（手動更新） |
| IAM グループ | CloudFormation |
| IAM グループにアタッチするポリシー | CloudFormation |
| ユーザー ↔ グループの所属関係 | Excel 台帳 + IAM コンソールでの手動アタッチ |

課題:
- Excel 台帳と実際の IAM の状態がずれる（台帳の更新漏れ）
- IAM ユーザーはパスワード・アクセスキーという長期認証情報を持ちがちで、MFA 強制やローテーションの統制が個々のユーザー任せになる
- ログイン先が IAM ユーザー個別のサインイン URL になり、アクセスポータルのような一元的な入口がない
- 退職者の棚卸しが台帳頼みになり、削除漏れのリスクがある

> **管理アカウントは 1 アカウントのみ**。そのため Identity Center の目玉機能である「複数アカウントへの一括権限配布」は今回の移行では使わない。今回移行するメリットは、あくまで①長期認証情報（パスワード・アクセスキー）を持つ IAM ユーザーを廃止し一時的な認証情報＋MFA 強制に寄せられること、②ユーザー管理とログイン導線が Identity Center の 1 か所に集約されること、③退職時にユーザーを 1 か所無効化すればアクセスを遮断できること、の 3 点。将来アカウントが増えても構成をそのまま流用できる点はおまけ。

## 移行後の管理体制（概念マッピング）

| 現状（IAM） | 移行後（IAM Identity Center） | 備考 |
|---|---|---|
| IAM ユーザー | Identity Center ユーザー（Identity Store User） | ログイン主体。AWS アクセスポータル経由でログイン |
| IAM グループ | Identity Center グループ（Identity Store Group） | 名前・構造はほぼそのまま踏襲できる |
| IAM グループにアタッチした IAM ポリシー | **Permission Set** | 「グループが持つ権限のまとまり」という点で IAM ポリシーの役割を引き継ぐ |
| IAM ポリシーの適用範囲（単一アカウント内で完結） | **Account Assignment**（Group × Permission Set × Account） | 今回は Account が 1 つだけなので実質「Group × Permission Set」の対応表と変わらない。ただし「誰がこのアカウントで何ができるか」を明示的な CFN リソースとして持てる点は 1 アカウントでも価値がある |
| Excel 台帳 | Identity Center の「ユーザー」一覧（コンソール／API が正） | 移行完了後、台帳としての Excel は廃止し Identity Center 自体を正とする |

ポイントは、IAM Identity Center では権限定義（Permission Set）と権限の割り当て先（Account Assignment）が分離されていること。1 アカウントのみの運用では Account Assignment は形式上「Group × Permission Set」を 1 アカウントに紐づけるだけの薄いレイヤーになるが、IAM グループへの直接ポリシーアタッチと違い「権限の定義」と「割り当て」が分かれることで、Permission Set 単体でレビューしやすくなるという構造上のメリットは残る。

## 移行方針

**段階移行（フェーズドマイグレーション）を推奨。**

理由:
- IAM ユーザーと Identity Center ユーザーは共存可能（同時に両方使える）なので、一括切り替えの必要がない
- グループ単位で移行すれば、問題が起きたときの影響範囲を限定できる
- CloudTrail で IAM ユーザーの実利用状況を確認しながら、安全に無効化・削除を進められる

進め方の粒度は「IAM グループ単位」を基本とする（既に CFN でグループ単位管理をしているため、Permission Set への置き換えもグループ単位で 1:1 対応させやすい）。

具体的な手順は [03-移行手順.md](./03-移行手順.md) を参照。
