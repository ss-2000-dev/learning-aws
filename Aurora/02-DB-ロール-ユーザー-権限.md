# 02. DB・ロール・ユーザー作成、権限付与とその確認

## まず用語を整理：ロール と ユーザー は同じもの

PostgreSQL では、昔は「ユーザー」と「グループ」が別物だったが、今は**すべて「ロール（ROLE）」に統一**されている。

| 用語 | 実体 | 違い |
|---|---|---|
| **ロール（ROLE）** | 権限のかたまり | 基本単位。これがすべて |
| **ユーザー（USER）** | = ログインできるロール | `CREATE USER` は「`LOGIN` 権限つきロールを作る」の別名 |

```sql
-- この2つはほぼ同じ意味
CREATE USER app_user PASSWORD 'xxx';
CREATE ROLE app_user LOGIN PASSWORD 'xxx';   -- LOGIN をつけるとユーザーになる
```

つまり：
- **人やアプリがログインする** → LOGIN 付きのロール（＝ユーザー）
- **権限をまとめて管理するグループ** → LOGIN なしのロール

## データベースを作成する

### 基本

```sql
CREATE DATABASE appdb;
```

### 商用向け：オーナー・文字コードを明示する（おすすめ）

```sql
CREATE DATABASE appdb
  OWNER = app_owner        -- このDBの所有者（先にロールを作っておく）
  ENCODING = 'UTF8'        -- 文字コード（日本語なら UTF8 一択）
  LC_COLLATE = 'C'         -- 並び順のロケール
  LC_CTYPE = 'C'
  TEMPLATE = template0;    -- ロケールを指定するなら template0 が必要
```

> 💡 **ロケール（LC_COLLATE）** は文字列の並び順に影響する。`'C'` はバイト順で高速・素直。日本語の辞書順ソートが必要な特別な要件がなければ `'C'` で問題ないことが多い。**後から変更できない**ので、要件が不明なら先にインフラ/リード担当に確認する。

### 作成したら確認

```
\l           -- データベース一覧（\list の略）
\l+          -- サイズなど詳細つき
```

## ロール / ユーザーを作成する

### アプリ用ユーザー（ログインする）

```sql
CREATE ROLE app_user
  LOGIN                       -- ログイン可能にする（＝ユーザーになる）
  PASSWORD 'strong_password'  -- パスワード
  CONNECTION LIMIT 20;        -- 同時接続数の上限（任意・DDoS的な暴走防止）
```

### 管理・グループ用ロール（ログインしない）

権限をまとめて管理するための「グループ」的なロール。

```sql
-- 読み取り専用グループ
CREATE ROLE readonly;
-- 読み書きグループ
CREATE ROLE readwrite;
```

### よく使う属性

| 属性 | 意味 |
|---|---|
| `LOGIN` / `NOLOGIN` | ログインできる/できない |
| `PASSWORD 'xxx'` | パスワード設定 |
| `CREATEDB` | DB を作れる |
| `CREATEROLE` | 他のロールを作れる |
| `CONNECTION LIMIT n` | 同時接続数の上限 |
| `VALID UNTIL '2026-12-31'` | パスワードの有効期限 |

> ⚠️ **Aurora では本物の `SUPERUSER` は作れない**。代わりに Aurora のマスターユーザーには `rds_superuser` というロールが付与されている。一般的な DB 構築はこれで十分できる。

## 権限を付与する（GRANT）／剥奪する（REVOKE）

### 権限の考え方（4つの階層）

PostgreSQL の権限は「入れ子」になっている。上から順に許可が必要。

```
① サーバーに接続できる         … ログイン権限（ロールのLOGIN属性）
② データベースに入れる         … GRANT CONNECT ON DATABASE
③ スキーマ（テーブルの入れ物）を使える … GRANT USAGE ON SCHEMA
④ テーブルを読み書きできる      … GRANT SELECT/INSERT/... ON TABLE
```

初心者が「ログインはできるのにテーブルが見れない！」となるのは、②③④のどこかが抜けているのが原因。

### グループロールに権限をまとめて付与する（推奨パターン）

個々のユーザーに直接付けるより、**グループロールに権限を付けて、ユーザーをそのグループに所属させる**のが管理しやすい。

```sql
-- 【読み取り専用グループ readonly に権限をつける】
GRANT CONNECT ON DATABASE appdb TO readonly;      -- ②DBに入れる
GRANT USAGE ON SCHEMA public TO readonly;         -- ③スキーマを使える
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;  -- ④既存の全テーブルを読める

-- 【今後作られるテーブルにも自動で SELECT を付ける】（重要）
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly;

-- 【読み書きグループ readwrite に権限をつける】
GRANT CONNECT ON DATABASE appdb TO readwrite;
GRANT USAGE ON SCHEMA public TO readwrite;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO readwrite;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO readwrite;  -- 連番(SERIAL/IDENTITY)用
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO readwrite;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO readwrite;
```

> 💡 **`ALTER DEFAULT PRIVILEGES` がなぜ重要か**
> `GRANT ... ON ALL TABLES` は「**今ある**テーブル」にしか効かない。この後に新しく作るテーブルには権限がつかず、「新しいテーブルだけ見れない」という事故になる。`ALTER DEFAULT PRIVILEGES` で「**今後作るテーブルにも自動でこの権限をつけてね**」と予約しておく。

### ユーザーをグループに所属させる

```sql
-- app_user を readwrite グループに入れる（readwrite の権限を引き継ぐ）
GRANT readwrite TO app_user;

-- 参照専用の別ユーザーを readonly に入れる
GRANT readonly TO report_user;
```

### 権限を剥奪する（REVOKE）

付与の逆。`TO` が `FROM` に変わる。

```sql
REVOKE INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public FROM app_user;
REVOKE readwrite FROM app_user;   -- グループから外す
```

### 個別テーブルへの付与例

```sql
-- 特定テーブルだけ許可
GRANT SELECT ON users TO readonly;
GRANT SELECT, INSERT ON orders TO app_user;

-- 特定カラムだけ許可（列レベル権限）
GRANT SELECT (id, name) ON users TO readonly;  -- id と name だけ見せる
```

## 権限・ロールを確認する

### ロール（ユーザー）の一覧と属性

```
\du           -- ロール一覧と属性（Superuser, Create DB など）
\du+          -- 説明つき
\du app_user  -- 特定ロールだけ
```

表示例：
```
                             List of roles
 Role name  |                Attributes                | Member of
------------+------------------------------------------+-------------
 app_user   |                                          | {readwrite}
 postgres   | Superuser, Create role, Create DB, ...   | {}
 readonly   | Cannot login                             | {}
 readwrite  | Cannot login                             | {}
```
`Member of` が「どのグループに所属しているか」。`Cannot login` がグループ用ロール。

### テーブルの権限を確認

```
\dp テーブル名     -- そのテーブルのアクセス権限（\z でも同じ）
\dp               -- 全テーブルの権限一覧
```

表示例（`\dp users`）：
```
 Schema | Name  | Type  |     Access privileges
--------+-------+-------+---------------------------
 public | users | table | app_owner=arwdDxt/app_owner+
        |       |       | readonly=r/app_owner       +
        |       |       | readwrite=arwd/app_owner
```

**記号の読み方**（`readonly=r/app_owner` = 「readonly は r(SELECT) 権限を持ち、それを付与したのは app_owner」）：

| 記号 | 権限 |
|---|---|
| `r` | SELECT（読み取り、**r**ead） |
| `w` | UPDATE（更新、**w**rite） |
| `a` | INSERT（追加、**a**ppend） |
| `d` | DELETE（削除） |
| `D` | TRUNCATE |
| `x` | 参照（外部キー、references） |
| `t` | トリガー |

### データベースへの接続権限を確認

```
\l+          -- Access privileges 列に DB レベルの権限が出る
```

### 「今の自分」の権限を確認

```sql
SELECT current_user;              -- 今のユーザー名
SELECT current_database();        -- 今のDB名
-- あるテーブルに対する自分の権限をチェック
SELECT has_table_privilege('users', 'SELECT');   -- t / f が返る
```

## 商用向けのおすすめ構成（まとめ）

```
app_owner (NOLOGIN)  … テーブルの所有者。DDLはこの人（またはマスター）で実行
  │
  ├─ readwrite (NOLOGIN グループ) … SELECT/INSERT/UPDATE/DELETE
  │     └─ app_user (LOGIN)       … アプリが使うユーザー
  │
  └─ readonly (NOLOGIN グループ)  … SELECT のみ
        └─ report_user (LOGIN)    … 集計・BIツールが使うユーザー
```

**ポイント**
- アプリは **マスターユーザーではなく `app_user`** で接続する（最小権限）。
- 権限は個人ではなく**グループロール（readwrite/readonly）に付ける**と、人が増えても楽。
- `ALTER DEFAULT PRIVILEGES` を忘れずに（新テーブルの権限漏れ防止）。
