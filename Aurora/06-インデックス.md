# 06. インデックス（索引）の効果と設定コマンド

## インデックスとは（本の索引にたとえる）

**インデックス**は、本の巻末にある「索引（さくいん）」と同じ。

- 索引がない本 … 目的の単語を探すのに**全ページを1枚ずつめくる**（遅い）
- 索引がある本 … 「その単語は123ページ」と索引を引いて**一発でたどり着く**（速い）

DB も同じで、インデックスがないと**テーブル全行を頭から順にスキャン**（フルスキャン）してしまう。インデックスがあると目的の行に直接ジャンプできる。

```
インデックスなし: SELECT * FROM users WHERE email = 'a@example.com';
  → 100万行を1行ずつ「これかな？違う」と全部チェック（遅い）

インデックスあり: 同じSQL
  → emailの索引を引いて該当行に直行（速い）
```

---

## どんな列にインデックスを貼るべきか

インデックスが効くのは、**検索・絞り込み・結合・並び替えに使う列**。

| 貼ると効く列 | 理由 |
|---|---|
| `WHERE` でよく絞り込む列 | 例: `WHERE email = ?`, `WHERE status = ?` |
| `JOIN` で結合に使う列（外部キー） | 例: `ON orders.user_id = users.id` |
| `ORDER BY` で並べ替える列 | 並び替えを高速化 |
| `UNIQUE` にしたい列 | 重複チェックも兼ねられる |

逆に、**貼らない方がいい / 効果が薄い**ケース：

- 更新（INSERT/UPDATE/DELETE）が非常に多い列（後述のデメリット）
- 値の種類が極端に少ない列（例: 男/女 の2種類だけ）→ 効果が薄いことが多い
- 行数が少ないテーブル → そもそもフルスキャンでも速い

---

## インデックスのデメリット（貼ればいいものではない）

| デメリット | 説明 |
|---|---|
| **書き込みが遅くなる** | INSERT/UPDATE/DELETE のたびにインデックスも更新が必要 |
| **ディスク容量を使う** | インデックスは別データとして保存される |

> 💡 だから「とりあえず全列に貼る」はダメ。**実際に遅いクエリ**を見つけて、**必要な列に貼る**のが基本。

## インデックスを作成するコマンド

### 基本

```sql
-- 書式: CREATE INDEX インデックス名 ON テーブル (列);
CREATE INDEX idx_users_email ON users (email);
```

> 💡 **命名規則**：`idx_テーブル名_列名` のように統一しておくと、後で見て分かりやすい。

### 複数列インデックス（複合インデックス）

`WHERE a = ? AND b = ?` のように複数列で絞る場合、まとめて1つのインデックスにできる。

```sql
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```

> ⚠️ **列の順番が重要**。`(user_id, status)` は「user_id だけの検索」「user_id と status 両方の検索」には効くが、「status だけの検索」には効きにくい。**よく絞る列を左**に置く。

### ユニークインデックス（重複禁止＋高速化）

```sql
CREATE UNIQUE INDEX idx_users_email_unique ON users (email);
-- email の重複を許さず、かつ検索も速くなる
```

### 部分インデックス（条件付き。省スペースで効率的）

一部の行だけを対象にするインデックス。無駄が少ない。

```sql
-- 「有効なユーザー」だけを対象にインデックスを作る
CREATE INDEX idx_users_active ON users (email) WHERE status = 'active';
```

### 式インデックス（加工した値で検索する場合）

```sql
-- 大文字小文字を無視して email 検索したい場合
CREATE INDEX idx_users_email_lower ON users (lower(email));
-- 検索側も lower(email) = lower('A@X.com') と書くと効く
```

## 【商用で最重要】CREATE INDEX CONCURRENTLY

### 普通の CREATE INDEX の落とし穴

通常の `CREATE INDEX` は、実行中そのテーブルへの**書き込みをロック（停止）する**。
大きなテーブルだと数分〜数十分かかることもあり、その間**アプリの INSERT/UPDATE が全部止まる**＝サービス障害になる。

### 解決：CONCURRENTLY（オンラインでインデックスを貼る）

```sql
CREATE INDEX CONCURRENTLY idx_users_email ON users (email);
```

`CONCURRENTLY` を付けると、**書き込みを止めずに**インデックスを作れる。本番の稼働中テーブルにはこちらを使う。

**注意点**：
- ⚠️ **トランザクションの中で実行できない**（`BEGIN;` の中や `--single-transaction` ではエラー）。単独で実行する。
- 通常版より作成に時間はかかる（が、サービスは止まらない）。
- まれに失敗すると「無効なインデックス（INVALID）」が残る。その場合は `DROP INDEX` して貼り直す。

```sql
-- 失敗して無効なインデックスが残った時の確認と削除
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_users_email;   -- 削除もCONCURRENTLYで
```

> 📌 **覚え方**：本番の既存テーブルに貼るなら **必ず CONCURRENTLY**。新規の空テーブルや構築中（まだ誰も使っていない）なら普通の CREATE INDEX でOK（速いので）。

## インデックスが効いているか確認する（EXPLAIN）

「貼ったのに速くならない」時は、**本当にインデックスが使われているか**を `EXPLAIN` で確認する。

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'a@example.com';
```

出力の読みどころ：

| 出てくる語 | 意味 |
|---|---|
| **`Seq Scan`**（Sequential Scan） | ❌ フルスキャン。インデックスが**使われていない** |
| **`Index Scan`** / `Index Only Scan` | ✅ インデックスが**使われている** |
| `Bitmap Index Scan` | ✅ インデックス使用（複数条件などで） |
| `actual time=...` | 実際にかかった時間（ミリ秒） |

```
-- 悪い例（インデックスなし）
Seq Scan on users  (cost=... rows=1000000) (actual time=0.5..320.1 ...)
     ↑ Seq Scan = 全件なめている。遅い

-- 良い例（インデックスあり）
Index Scan using idx_users_email on users  (actual time=0.03..0.05 ...)
     ↑ Index Scan = 索引を使っている。速い
```

> 💡 `EXPLAIN` だけなら実行計画の予想のみ。`EXPLAIN ANALYZE` は**実際に実行して**計測する（本番の UPDATE/DELETE に ANALYZE を付けると実際に変更されるので、SELECT 以外は BEGIN; ... ROLLBACK; で囲むこと）。

## インデックスの確認・管理コマンド

```
\di                    -- インデックス一覧
\di+                   -- サイズつき
\d users               -- テーブルの詳細（下部に Indexes として表示される）
```

```sql
-- あるテーブルのインデックスを SQL で確認
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'users';

-- インデックスのサイズを確認
SELECT pg_size_pretty(pg_relation_size('idx_users_email'));

-- 使われていない（無駄な）インデックスを探す
SELECT relname, idx_scan FROM pg_stat_user_indexes ORDER BY idx_scan ASC;
--  idx_scan が 0 に近い = ほとんど使われていない → 削除候補
```

### インデックスの削除・再構築

```sql
DROP INDEX idx_users_email;                 -- 削除
DROP INDEX CONCURRENTLY idx_users_email;    -- 本番はこちら（ロックしない）
REINDEX INDEX idx_users_email;              -- 再構築（肥大化した時など）
```

---

## まとめ

1. **遅いクエリの WHERE / JOIN / ORDER BY の列**にインデックスを貼る。
2. 命名は `idx_テーブル_列` で統一。
3. **本番の既存テーブルには `CREATE INDEX CONCURRENTLY`**（サービスを止めないため）。
4. 貼ったら `EXPLAIN ANALYZE` で **`Index Scan` になっているか**確認。
5. 貼りすぎ注意（書き込みが遅くなる）。使われていないインデックスは消す。
